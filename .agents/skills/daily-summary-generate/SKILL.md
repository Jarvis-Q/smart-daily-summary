# 每日工作摘要生成器 · 生成（Codex 版）

> 本 skill **只采集与生成，绝不发送**。发送是独立的 `daily-summary:send`（见该 skill）。
> 两者严格分离，禁止在本 skill 内调用 `send_report.py`。

## 插件根目录怎么取

本 SKILL.md 位于 `<插件根>/.agents/skills/daily-summary-generate/`。经软链安装时
（如 `~/.agents/skills/daily-summary-generate` → 仓库内目录），请先用 `readlink` 解析
真实路径，**取其上三级即插件根**。据此拼出脚本绝对路径再执行——不要写死任何绝对路径。

## 执行流程

1. **数据采集**：运行插件根目录下的采集脚本
   ```bash
   python3 <插件根>/scripts/gather_data.py          # 默认今天
   python3 <插件根>/scripts/gather_data.py day=2     # 补采昨天（day=N 即回退 N-1 天）
   ```
   该脚本仅采集、不发送。它会**自动发现当日所有工作过的目录**（Claude 会话 cwd +
   Codex 会话 cwd + config 的 `extra_git_dirs` 兜底），逐个 Git 仓库采集提交，
   **当天跑一次即可覆盖全天全部工作**。脚本缺失、无 Git 仓库或目录不存在时优雅降级。
   输出分「Claude Code 对话与用量」「Codex 对话与用量」两节，并给出跨端合计。

2. **隐性工作补充（强制交互）**：向用户发送以下消息并等待回复：
   > 基础数据已收集。请快速补充（没有可回复"无"）：
   > 1. **沟通/会议**：重要决议、跨部门沟通或邮件指示？
   > 2. **卡点/排坑**：技术障碍、环境问题或 Bug 及解决过程？
   > 3. **知识/资源**：新概念、新工具或关键数据口径？

3. **任务字段采集（强制交互）**：拟定任务拆分后，为**每个任务**采集两个字段。
   以编号选项的形式一次性列出（多个任务合并成一轮提问，不要每个任务单独一轮），
   用户回复编号或直接输入名称均可：

   - **工作分类**：读取 `<插件根>/data/categories.json`（中文名 → code 的全量字典），
     根据任务内容推荐 **3 个**最贴合的分类作为选项。用户也可直接输入中文名或 code。
     输入值不在字典中时**必须重问一次**，不要擅自取近似值。
   - **所属项目**：按三级查找，能快则快、找不到才联网：
     1. 先执行 `python3 <插件根>/scripts/projects.py frequent`，列出按历史发送统计的
        高频项目（至多 8 条），连同 `config.json` 中 `defaults.project_name` 配置的默认项一起作为首选选项；
     2. 都不合适时，根据任务内容拟一个关键词执行
        `python3 <插件根>/scripts/projects.py search <关键词>`（本地缓存，至多 5 条）；
     3. 仍未命中或用户认为是新建项目时，执行
        `python3 <插件根>/scripts/projects.py remote-search <关键词>`
        （联网刷新缓存后匹配），让用户重新给关键词可再搜一次。

   > **项目数据是公司内部数据**：只用于本步骤的选择与后续发送映射。
   > 不要把 search / remote-search / frequent 的输出转贴到日报正文、总结文字或任何其他
   > 位置，也不要一次性列出全量项目列表。

4. **生成与保存**：结合数据与用户回复生成标准化 Markdown 日报。
   - **保存路径与文件名严格使用脚本输出的"日报保存位置"那一行**，文件名形如
     `daily-summary-YYYY-MM-DD.md`——send 的自动定位依赖此命名。
   - **token 与 AI 耗时必须采用脚本输出的真实数值**（脚本已汇总 Claude 与 Codex 两端的
     "真实 token 合计"与"AI 机器耗时合计"，口径同 cc-usage、已剔除人操作时间），
     **严禁自行估算**。当日报拆为多个任务时，各任务的 `Token 消耗量`/`AI 辅助耗时`
     之和应等于脚本给出的当日真实合计（按投入比例分摊）。

5. **结束提示**：告知用户日报已保存，提示可通过 `daily-summary:send` 发送，或在编辑器中修改后再发送。

## 补发历史日报

`gather_data.py` 已内置 `day` 参数：`day=N` 换算为「今天回退 N- 1 天」（`day=1` 今天、
`day=2` 昨天…，`day<1` 报错）。跨零点场景尤其有用：凌晨补写前一天日报时用 `day=2`，
避免把刚过午夜的空数据当成"今天"。

## 安全护栏（务必遵守）

日报正文会被发送到私有服务器。本项目为医疗语境：

- **严禁**在日报中写入患者姓名/病历号/手机号/身份证号等个人标识，以及任何密钥、令牌、密码。
- 只写"做了什么"，不写敏感原文。
- 发送脚本还会在出网前对疑似凭证做二次脱敏兜底，但那是兜底，不是许可。

## 输出格式规范

**严禁修改标题结构和括号内的字段名，否则会导致 `send_report.py` 解析失败：**

```markdown
### 任务 X: [任务名称] (预估总耗时: X小时)
- 工作分类: [中文分类名]
- 所属项目: [项目全名]
- AI 辅助耗时: X 小时
- Token 消耗量: X tokens
- 工作详情:
  - 具体工作内容 1
  - 具体工作内容 2
```

说明：

- `AI 辅助耗时` 与 `Token 消耗量` **取自脚本输出的真实数据**（两端会话日志汇总），
  多任务时按投入比例分摊，各任务之和等于当日真实合计。
- `预估总耗时` 为该任务的整体工时（含非 AI 部分），可由你根据工作量合理判断。
- 用户补充的隐性工作（沟通/卡点/知识沉淀）可归纳为独立任务，其 AI 耗时/Token 通常为 0。
- **正文直接以 `### 任务 1:` 开头即可**，不必加日报标题。
- `工作分类` 写**中文分类名**（如 `开发`），取值必须来自 `data/categories.json`。
- `所属项目` 写**项目全名**，必须与 `projects.py` 返回的 `name` 完全一致——
  发送时按精确匹配转 id，写错或简写会回退到默认项目。

> **服务端硬约束（拆分任务时必须遵守，否则整单发送失败）**：
> - **单个任务的 `预估总耗时` 必须落在 `0.5 ~ 4` 小时区间内（含两端）**。服务端逐项校验，
>   任一任务越界即返回 `code:500`，**整份日报都发不出去**：
>   - 小于 0.5 → `工作耗时最少0.5小时`
>   - 大于 4 → `工作耗时不能大于4小时`
> - 因此**拆分粒度要卡在这个区间里**：零碎工作**向上合并**进相关任务；
>   大块工作**向下拆分**成多个 ≤4 小时的任务（按真实子结构拆，不要为凑数字虚报）。
> - 每日任务数不限，总工时无上限，**只卡单项区间**。
> - **`AI 辅助耗时` 与 `Token 消耗量` 可以为 0**，不受此约束——会议、卡点等隐性工作正常填 0。
